## Тесты
- `npm test` — компонентные тесты в режиме наблюдения (Vitest + React Testing Library + MSW)
- `npm run test:run` — компонентные тесты один раз (так же их запускает CI)
- `npm run e2e` — E2E (Playwright), нужен запущенный локальный API (`npm run dev` в agromarket-api); Vite Playwright поднимет сам
- `npm run e2e:smoke` — только тесты с меткой `@smoke` (ничего не меняют в базе)
- `BASE_URL=https://agromarket-dmtrp.vercel.app npm run e2e:smoke` (или `npm run e2e:prod`) — smoke против продакшена
- Тесты фермера берут логин/пароль из `.env.e2e` (скопируйте `.env.e2e.example`; файл в `.gitignore`)

### Какие недоделки нашли тесты
- Поле e-mail было подписано «Email», а формы добавления товара вообще не имели `<label>`: тесты не находили поля по подписи, это ошибка доступности.
- `Catalog` запрашивал относительный `/api/products` вместо `API_URL`: MSW (и сервер на другом домене) такой запрос не обслуживает. Ошибка загрузки не имела `role="alert"`.
- Формы показывали только общий текст ошибки и не выводили `details` из ответа 400 (ЛР11). Теперь `apiFetch` передаёт `status` и `details`, а формы показывают сообщения по полям.
- В карточке товара не было ссылки на страницу товара и категории; не было страницы `/products/:id` и маршрутов вообще.
- Форма добавления была доступна только `admin`, хотя товары добавляет фермер; не было удаления товара через интерфейс.
- `vi.spyOn(fetch)` не снимался после теста — вызовы копились между тестами (добавлен `vi.restoreAllMocks()` в `setup.js`).
- Vitest подхватывал `src/e2e/*.spec.js` (исключение было только для корневой `e2e/`).
- В CI-файле было два ключа `jobs:` (второй перезаписывал первый), компонентные тесты в CI не запускались; ежедневный workflow гонял полные E2E (с регистрацией) против продакшена.

### Почему MSW, а не vi.mock(fetch)
MSW перехватывает запрос на уровне сети: компонент и `apiFetch` работают как в браузере — строят URL, ставят заголовки, читают статус и JSON. Тест проверяет настоящий код целиком и не зависит от того, как именно сделан запрос (fetch, axios, обёртка). `vi.mock` подменяет модуль: тест знает про внутреннее устройство и ломается при рефакторинге, а ошибки в адресе или заголовках не ловит. Обработчики MSW описывают API один раз и переиспользуются; `server.use` в тесте задаёт свою ситуацию (пусто, 500, 429, медленная сеть).

### Почему полные E2E нельзя запускать на продакшене, а smoke — можно
Полные E2E меняют данные: регистрируют пользователей, создают и удаляют товары, упираются в rate limit. На продакшене это мусор в базе у реальных пользователей, риск удалить чужое и заблокировать вход. Smoke-тесты (`@smoke`) только читают: открывают главную и страницу товара. Они ничего не меняют и за секунды отвечают на вопрос «живо ли приложение после деплоя».

### Ошибку цены -500 показал браузер или сервер? Почему нужны обе проверки
В интерфейсе ошибку показал **браузер**: у поля `min="1"`, форма не отправилась (`validity.rangeUnderflow`). Тест `farmer.spec.js` дополнительно шлёт POST в обход формы — **сервер** (zod) отвечает 400. Браузерная проверка — для удобства пользователя (мгновенно, без запроса), но её легко обойти (DevTools, curl, Postman). Защиту данных даёт только серверная проверка, поэтому нужны обе.
